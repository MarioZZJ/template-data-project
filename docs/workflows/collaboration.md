# 研究与论文协作

## Multica 与 GitHub 分工

Multica 维护研究任务、阶段授权、执行依赖、待决事项及验收。GitHub 用于具体代码和正文修改的审阅。需要两者协同时互相链接，不复制两套实时任务状态。

阶段开始就确定必要独立复核；普通任务由执行者自检，不因一般恢复或模型切换再添审批。阶段验收由用户进行，已获同一授权的动作不重复请求许可。

## 固定负责人和评论派工

父、子 issue 的负责人始终为 Butler，执行成员通过同一 issue 的评论提及承接工作，不以 `issue assign` 交接。成员完成、失败或发现差距，都评论提及 Butler，给出结果、产物、自检、影响和剩余范围；自己的分工完成不代表整项 issue 完成。

Butler 负责全任务和接续。已有授权内没有实质决策就继续评论派工；涉及研究取舍、超范围或阶段验收时提及用户并提供简短建议。普通成员自检仍有效，交回 Butler 不额外新增独立复核。

## 正文批注与修改

对当前正文提出意见时，可使用 GitHub Issue，并附指向具体 commit 和行位置的永久链接，说明证据、建议方向与需要作者决定的事项。已有 Multica 研究任务时提供关联，不为没有正文改动的问题创建空 PR。

实际改写使用小 PR，围绕一个论证点、图注、术语统一或一组紧密关联的图表说明变化。PR 说明研究或数据影响及实际检查；不通过无意义空白变化制造 diff。超出本次修改的大段新意见回到关联任务或正文批注。

## 运行记录与平台交付

成员先把分工结果或失败评论交回 Butler，不在局部完成时提前改变全任务状态。Butler 核对完整范围与研究影响，在属于原 issue 的执行中以 `--no-start` 进入 `in_review`，再按[研究执行](research-execution.md)读取版本并发布正式交付评论和记录。正式发布后该来源执行不再修改 issue；若有新要求，由后续 Butler 执行读取后接续。桥接程序只自动关闭已登记子任务，父阶段等待人工验收。新意见或版本冲突使旧交付失效，不能绕过新要求强制关闭。

评论默认以结论和下一动作为先，普通评论不超过 300 字、决策评论不超过 600 字；详细证据链接实际文件。图示帮助解释，文字仍独立表达结论和待决事项；图像工具不可用时如实说明。

## PDF 与本地检查

PR workflow 基于 base 与 head 生成 `manuscript-diff.pdf`；Release workflow 编译阅读版 `main.pdf`。PDF 是沟通或发布产物，TeX 和正式图表由 Git 维护，数据来源由索引追溯。

```bash
make check-tex-style
make manuscript
BASE_REF=origin/master HEAD_REF=HEAD make manuscript-diff
```

提交前核对正文、实验解释与正式图表证据，不依据过期看板判断结果。Git 操作保留已有改动、显式选择提交范围，并遵守本机署名和当前发布授权。
