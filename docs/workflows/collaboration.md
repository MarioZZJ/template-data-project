# 研究与论文协作

## Multica 与 GitHub 分工

Multica 维护研究任务、阶段授权、执行依赖、待决事项及验收。GitHub 用于具体代码和正文修改的审阅。需要两者协同时互相链接，不复制两套实时任务状态。

阶段开始就确定必要独立复核；普通任务由执行者自检，不因一般恢复或模型切换再添审批。按登记的 auto、independent 或 human 政策完成阶段；明确的人工检查点才等待用户，已获同一授权的动作不重复请求许可。

## 研究负责人和完整执行者

项目推进总 issue 和阶段由普通 Research Lead Agent 负责；成果子任务由实际完整交付者负责。Lead 可以亲自实施短任务，也可以委派独立成果。不要通过原生 `@squad` 路由要求同一领队同时承担实施。

派工只选择 assignment 或明确 agent mention 中的一条路径，读回真实运行；不能连续 assignment 加 mention 造成重复启动。阶段和必需成果明确 `stage`，没有显式依赖时按已确认的科学顺序串行；取消前置不代表输入已经产生。

执行者对完整实现、检查、解释、保存和交付负责。只有实质研究取舍、缺少授权、超出额度或 human 检查点才提请用户决定；普通工作不增加逐项 Lead 审批。共享技能逐成员绑定，只覆盖研究执行角色，不能改变同工作区的运维角色。

## 正文批注与修改

对当前正文提出意见时，可使用 GitHub Issue，并附指向具体 commit 和行位置的永久链接，说明证据、建议方向与需要作者决定的事项。已有 Multica 研究任务时提供关联，不为没有正文改动的问题创建空 PR。

实际改写使用小 PR，围绕一个论证点、图注、术语统一或一组紧密关联的图表说明变化。PR 说明研究或数据影响及实际检查；不通过无意义空白变化制造 diff。超出本次修改的大段新意见回到关联任务或正文批注。

## 运行记录与平台交付

实际完整交付者在属于原 issue 的执行中核对范围与研究影响，以 `--no-start` 进入 `in_review`，再按[研究执行](research-execution.md)读取版本并发布交付评论和记录。正式发布后该来源执行不再修改 issue；新要求由后续执行重新读取。服务仅按已登记政策和条件版本收尾：auto 普通成果可自动完成，independent 要求固定内容的独立复核，human 等待人类；未接通范围不能声称已自动化。

完整阶段通过项目推进总 issue 的 stage 通知唤醒 Lead，由它核对下一阶段真实输入和有效授权。计划列出了下一阶段不等于已授权。新意见或版本冲突使旧交付失效，不能绕过新要求强制关闭。
评论默认以结论和下一动作为先，普通评论不超过 300 字、决策评论不超过 600 字；详细证据链接实际文件。图示帮助解释，文字仍独立表达结论和待决事项；图像工具不可用时如实说明。

## PDF 与本地检查

PR workflow 基于 base 与 head 生成 `manuscript-diff.pdf`；Release workflow 编译阅读版 `main.pdf`。PDF 是沟通或发布产物，TeX 和正式图表由 Git 维护，数据来源由索引追溯。

```bash
make check-tex-style
make manuscript
BASE_REF=origin/master HEAD_REF=HEAD make manuscript-diff
```

提交前核对正文、实验解释与正式图表证据，不依据过期看板判断结果。Git 操作保留已有改动、显式选择提交范围，并遵守本机署名和当前发布授权。
